# Миграция 0003_stage2_hotfix

## Зачем (причина)

На боевых БД, созданных **до** правок `before_stage_3`, миграция `0002_stage2_catalogs`
уже была применена и повторно не запускается (механизм миграций пропускает версии,
записанные в `schema_migrations`). В результате правки, внесённые в 0002 позже
(`parallel_group` для ADR-12 и удаление сезонных колонок), на таких базах **не
выполнились**, а код уже ожидает новую схему → ошибки (в т.ч. 500 на страницах
программ и зон).

**Править применённую миграцию 0002 запрещено** — это переписывает историю и
ломает воспроизводимость прогонов. Разрыв схемы устраняется новой миграцией 0003.

## Что делает

1. `program_zones`: `ALTER TABLE ... ADD COLUMN parallel_group TEXT` — через
   проверку `_has_column` (на новых БД колонка уже есть из 0002 — no-op).
2. `zones`, `programs`: `ALTER TABLE ... DROP COLUMN season_start / season_end`
   для старых БД, где колонки остались (через `_table_exists` + `_has_column`;
   SQLite >= 3.35; на новых БД колонок нет — no-op).

## Идемпотентность

- Все операции защищены проверками наличия таблицы/колонки;
- миграция не падает на новых БД (где правки 0002 уже применены);
- на SQLite < 3.35 DROP COLUMN пропускается (код сезонные колонки не использует).

## Проверка после применения

- `PRAGMA table_info(program_zones)` содержит `parallel_group`;
- `PRAGMA table_info(zones)` / `PRAGMA table_info(programs)` НЕ содержат
  `season_start` / `season_end`.

## Откат

Не предусмотрен (как и у остальных миграций проекта); перед экспериментами —
копия БД в `backups/`.
