# ADR-19 — этап 9: интервальные блокировки и подтверждаемая нормализация

Дата: 26.10.2026. База: main 9cab288. Ветка feature/stage9-locks-normalization.
Основание: ТЗ Этап 0 §§9A/9B, API 4.8/4.12, Артефакт БД §13, ADR-13.

## 9A: блокировки

Сохраняем zone_locks и её исторический kind CHECK. Новые start_ts/end_ts — UTC
секунды, полуоткрытый интервал [start,end); end=NULL — бессрочно. block_type:
auto/all/service; все запрещают automatic, all/service также manual. block_manual
можно включить для auto. Legacy kind читается прежним способом; новые типы хранятся
отдельно без переписывания старых миграций. Снятие soft: active=0, released_by/at,
аудит и сохранение истории. Quick-block: час/24 часа/число часов, либо точные даты.

Компилятор после погоды проверяет реальные UTC-интервалы water steps каждой
occurrence, включая offset и будущие дни. Если zone пересекает lock, она пропускается
целиком в данном run; свободные зоны остаются. Освободившийся water slot превращается
в relay-off soak, чтобы сдвиг последующих шагов не попал в другую блокировку. Другие
длительности не сокращаются. Полностью пустой run исключается и отмечается
zone_locked. Пропуски видны в metadata, журнале/уведомлениях и heatmap.

Manual проверяется в общем сервисе команд при приёме и перед каждой публикацией,
включая повтор. override_block не обходит это правило: настройка/роль override в
этой реализации не вводятся. Stop/close доступны всегда. API create/release вызывает
compile-and-send и возвращает delivery/error. Ошибка доставки не откатывает lock:
оператор видит запрет на сервере и отдельное состояние доставки.

BlockEnforcer (1 с) останавливает online активные зоны при наступлении start:
auto-only не останавливает manual/service, all/service останавливает все. Stop
дедуплицирован по контроллеру на 5 с; при недоставке повтор возможен. При expiry
пересобирает горизонт; явное снятие также пересобирает. Stop может остановить весь
контроллер, чтобы не зависеть от поддержки частичного вмешательства в active run.

Сервер не способен физически отозвать старое расписание offline-контроллера. Это
ограничение видно в UI и manual runbook: гарантировать запрет до ACK/подтверждённой
остановки нельзя. Локальная физическая клавиатура/firmware — этап 10, не 9.

## 9B: независимый optimizer

Детерминированный модуль core/normalization/optimizer.py получает уже скомпилированные
weather/season/cycle-soak/parallel steps. Меняет только start_minute_local целого run,
внутри его исходного дня и общего заданного окна. Не меняет source program, water/soak
секунды, группы, дни/частоту и погодные коэффициенты (ADR-13). Day — один день,
week — семь исходных дней. Разбиение runs/перенос между днями — возможное дальнейшее
расширение, а не обязательный метод оптимизации: без агрономических ограничений это
может нарушить интервалы полива. Недельные суточные объёмы здесь намеренно неизменны.

Расход оценивается по минимум 3 корректным одиночным finished событиям каждой зоны
за 90 дней: сумма измеренных литров / water_sec * 60. Aborted/anomaly/zero/parallel
из выборки исключены. Нет данных — job error с причиной, не подстановка случайного
expected_flow. Снимок содержит count/lpm источников, controller IDs, window, before/
after runs и hashes. Дополнительная параллельность внутри контроллера не создаётся.
Общая нагрузка оценивается по выбранным контроллерам; неизвестные внешние сети/
давление не моделируются и явно предупреждаются. Исходные parallel groups сохраняются.

Целевая функция: 15-минутная средняя нагрузка с сохранением оценочного объёма;
reduce_peaks минимизирует peak затем L2, smooth_consumption — L2 затем peak.
Greedy largest-volume-first с deterministic tie-break. Проверяются отсутствие
пересечений на контроллере, сохранение дня, окна и lock intervals. Это эвристика,
не доказательство глобального оптимума или достаточного давления. Невозможное
размещение — error; худшая замена валидного исходного плана не предлагается.

## Предложение и применение

normalization_jobs: processing/ready/error/applied/rejected. Расчёт синхронен внутри
ограниченного worker request (API не блокирует event loop); максимум 50 controllers,
1000 runs, day/week. normalize никогда не запускается автоматически по телеметрии.
Предложения хранятся JSON в SQLite транзакционно; payload_path nullable. Так сохраняется
история без новой несогласованности файлов предложения и БД.

Apply требует именно confirm=true даже если generic settings пытаются выключить
confirmation. Не применяется к уже начавшемуся времени. Сверяет source snapshot
настройки/зоны/программы/погода/lock/статистика/overrides; volatile last_seen/mode
контроллера не инвалидирует предложение. Изменения →409, пересчитать. Повтор applied
не создаёт новые версии; rejected повторно применить нельзя.

Под расписанным mutex + BEGIN IMMEDIATE записываются per-controller/program/date
overrides, повторно компилируется текущий полный горизонт (он не обрезается до одного
дня предложения), проверяются точное соответствие выбранных runs и неизменность steps,
создаются версии controller_schedules и audited applied status. После commit вызывается
существующая доставка с next_run/offline политикой; ошибки возвращаются отдельно.
Принятие оператором не равно ACK контроллера. On hello/recompile overrides сохраняются,
normalization metadata детерминирована. Устаревшие overrides за прошлые даты сохраняются
как история и не влияют на новые даты; lifecycle удаления — отдельная retention policy.

Heatmap рисует будущий план только для acknowledged версии, planned_cells/tooltip
отделяют его от факта. Sent/compiled без ACK не выдаётся за действующее расписание.

## Совместимость и восстановление разработки

0013 additive, старые миграции не меняются. Downgrade сохраняет записи аудита и
подтверждённые overrides. До deployment backup; при откате на pre-stage9 код не
заявлять сохранение новых блокировок/переносов. При сбое разработки — конец WorkBook,
docs/STAGE9_PROGRESS.md и последний remote commit. Каждый блок сохраняется отдельным
commit+WorkBook+push. Main в этой сессии не меняется.
