# Этап 9 — инструкция проверки и восстановления

Ветка: feature/stage9-locks-normalization, основа main 9cab288.
Решения и ограничения: docs/adr/ADR-19-stage9.md. Миграция 0013 additive.
Перед обновлением backup БД, schedules и архивов. Использовать отдельный
POLIV_DATA_ROOT, один worker Uvicorn; реальные клапаны для автотестов не нужны.

## Автоматическая приёмка

1. Python 3.13, `python -m pip install -r requirements.lock`, `pip check`.
2. `python -m pytest server/tests -q --disable-warnings --tb=short`.
3. Optional Playwright 1.64.1 + Chromium/deps:
   `python -m server.tools.browser_smoke`, `python -m server.tools.stage9_smoke`.
   Stage9 smoke проверяет реальный FastAPI/SQLite с fake MQTT через браузер.
4. Установить executable Mosquitto, `python -m server.tools.mqtt_smoke`.
   Используется отдельный loopback broker на случайном порту. Проверяется в том
   числе отсутствие publish blocked manual и успешный запуск после release.
5. Дождаться tests/browser/mqtt jobs на SHA ветки в Actions. CI включён для feature/**.

## Ручная проверка 9A

Войти operator/admin, меню «Блокировки / нормализация» (`/stage9`).
Создать зону/программу до проверки; ID зоны доступен в каталоге.

- Выбрать auto, причину, «На час»/«На 24 часа»; проверить запись и даты.
- Новая версия расписания должна исключить только затронутые occurrence; утренний
  запуск не исчезает из-за lock в полдень. Следующий день после expiry сохранён.
- Auto-only разрешает manual. All/service запрещает manual на входе и перед
  публикацией, включая пересечение duration с будущим start. Stop/close доступны.
- Создать active block на работающую online-зону: сервер запрашивает stop_all,
  новая версия доставляется по безопасной существующей политике; проверить ACK.
- Снять lock: active=0, released_by/at, журнал, пересборка расписания.
- С отключённым broker доставка явно error/not sent. Сохранённая серверная lock
  не означает физический запрет на offline box: проверить локально/не подключать воду.
- Посмотреть heatmap: blocked интервалы и уведомления zone_block/zone_block_skip.

## Ручная проверка 9B

Нужно минимум 3 корректных одиночных finished события КАЖДОЙ затронутой зоны за
90 дней с положительным water_sec/volume, без аварий. Parallel/aborted не годятся
как точное обучение расходу зоны. Недостаток данных — задача error с причиной.

- Выбрать будущую дату, day/week, controller IDs, target и окно 0..1440 минут.
- Рассчитать: появляется ready job и proposal before/after, оценочный пик/объём,
  список переносов и предупреждения. До подтверждения overrides/версии не меняются.
- Попытаться применить без checkbox: ошибка. Подтвердить: новые версии и delivery.
- Повтор apply не создаёт дополнительные версии. Отклонённый proposal не применяется.
- После расчёта изменить зону/lock/погоду/статистику: apply возвращает 409 stale,
  нужно новое предложение. Временные last_seen контроллера proposal не меняют.
- После schedule ACK heatmap показывает новый будущий план. Он помечен как план,
  не факт. Sent без ACK не выдаётся за доставленное расписание.
- Проверить неизменность water/soak, parallel membership, исходных программ и погоды.
  Нормализация переносит whole runs только ВНУТРИ исходного дня. Week обрабатывает
  семь дней; распределение объёмов между днями/разбиение программ не заявлены.
- Давление/гидравлика вне измерений; optimizer не включает новую параллельность,
  не гарантирует глобальный оптимум и не заменяет проверку доступной сети.

## API

GET/POST `/api/v1/zone-blocks`, DELETE `/api/v1/zone-blocks/{id}`;
GET `/api/v1/zones/{id}/blocks`, POST `/api/v1/zones/{id}/quick-block`.
Создание: zone_id, start_ts, end_ts, kind=auto/all/service, block_manual, reason.
Quick: duration_hours, kind, block_manual, reason. Даты UTC Unix, [start,end).

POST/GET `/api/v1/normalization/jobs`, GET `.../{id}`, GET `.../{id}/proposal`,
POST `.../{id}/apply` с `{ "confirm": true }`, POST `.../{id}/reject` с `{}`.
Job: scope, date, controller_ids, target, window_start_minute/window_end_minute;
respect_zone_blocks/respect_season/respect_weather нельзя выключать.
GET/PUT `/api/v1/settings/normalization`; confirm всегда обязателен, min_events>=3.
Read blocks разрешён viewer; normalization operator/admin; остальные записи operator/admin.

`git status -sb`, `git log -6 --oneline`, сверить remote ветку и незакоммиченные файлы.
Не переписывать миграцию уже применённой схемы/исходные данные. Не применять proposal
по старому UI без status/snapshot проверки. Последовательность checkpoint commits
содержит проверенный объём, результаты тестов, остатки и следующий шаг.

## Откат

Не сливать/развёртывать автоматически. Сначала остановка/backup. 0013 downgrade
сохраняет таблицы, аудиты и поля. Pre-stage9 приложение не обеспечивает новые типы
блокировок и accepted overrides: откат требует осознанного возврата к проверенному
расписанию, а не молчаливого удаления таблиц. Старые payload-файлы с orphan после
rollback БД не отправлять вручную: источник истины — controller_schedules.
