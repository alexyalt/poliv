## Runtime-файлы в Git: миграция без потери рабочей БД

В этой ветке намеренно не создаётся deletion commit для уже отслеженных data/logs:
при обычном pull он мог бы удалить файлы существующей установки. Новые runtime
файлы игнорируются. Полное закрытие F09 требует отдельной эксплуатационной миграции:

1. Остановить приложение либо создать консистентную SQLite backup API копию;
   сохранить config.local.toml, data, архив по обоим старому/новому путям и журналы.
2. Проверить восстановление копии в отдельный POLIV_DATA_ROOT.
3. Перенести рабочие данные в независимый каталог вне checkout, явно настроить пути.
4. Только после этого убрать точный перечень runtime из индекса Git отдельным PR.
   Не выполнять `git rm` над единственной рабочей копией данных.
5. Для чистой установки использовать новый data root. Не считать пользовательскую
   data/poliv.db в истории проекта production seed.

Не переписывать историю Git автоматически. Проверка старой истории на действующие
секреты и отзыв найденных токенов — отдельная задача.

## Обновление и откат

Сначала backup БД/архивов и тестовая копия. Установить requirements.lock на Python
3.13, выполнить полный pytest, затем один worker приложения. Миграция 0011 добавляет
два столбца, не меняет старые пути/файлы. Новые партии требуют companion manifest.
При откате сохранить новую БД и файлы: старый reader не знает v2 отношений и не
должен использоваться для restore новых партий. Старый daemon должен быть отключён
до отката архивного кода, иначе он снова будет писать небезопасный дневной append.

Архив не является резервной копией всей системы. Перед реальной водой нужны
Mosquitto/ESP32, браузерная и нагрузочная приёмки, безопасное отключение питания,
локальный failsafe; результат pytest этого не подтверждает.


## Обновление: завершение программных доработок 8.S

База продолжения: aea4061. Историческая таблица выше описывает первый проход;
актуальные изменения этого продолжения:

- F01: async workers ограничены 16 обычными и 64 остановками; stop имеет отдельную
  ёмкость, shutdown отменяет ожидания и присоединяет worker threads.
- F07/F11: основной conn и conn MQTT/ScheduleService заменены ScopedConnection:
  запрос/задача + thread имеют собственное native соединение, закрываемое в finally.
  Вложенные сервисные транзакции используют savepoint, не commit чужой операции.
  Контексты MQTT dispatch, maintenance и emergency/command worker обёрнуты scope.
- F08: команды с ожиданием ACK, compile/preview, JSON/CSV отчёты, heatmap и погодный
  preview выполняются вне event loop. Медленный отчёт не блокирует независимый HTTP.
- Дедупликация: миграция 0012 хранит processed_events отдельно от архива; event/flow/
  schedule имеют собственные атомарные consumer markers. Повтор после ротации не
  создаёт новое событие и не увеличивает flow_daily. Данные, архивированные до
  миграции без UID ledger, не могут быть надёжно backfill.
- F06: новые event-zone записи делят общий объём между зонами; отчёт нормализует
  исторические полные-per-zone значения к объёму родителя. Это оценочная атрибуция,
  не измерение расхода каждого клапана; общего множителя объёма больше нет.
- Архив: flow/weather restore реализован; пакеты выборки ограничены 1000 строками,
  rotate_all обрабатывает до 100 партий на тип за цикл, оставшийся backlog безопасно
  остаётся в БД. Durable write lock длится одну ограниченную партию.
- UI: седьмой отчёт missed в JSON/CSV/вкладке, семь дней heatmap последовательными
  дневными запросами без единого огромного ответа. Текущий offline — индикатор
  доступности сейчас, исторических интервалов связи пока нет.
- Сессии: запись touch ограничена интервалом, cookie продлевается вместе с активной
  сессией. /health — liveness, /ready проверяет БД и MQTT и возвращает 503 без брокера.
- F09: добавлен неразрушающий server.tools.prepare_runtime с SQLite backup API,
  отказом при существующем destination и сохранением исходных файлов. Автоматическое
  удаление ранее отслеженных runtime всё ещё намеренно не выполняется: владельцу
  существующей установки сначала требуется перенести данные вне checkout.

CI остаётся шаблоном: текущий PAT не имеет workflow scope. Это ограничение GitHub,
а не незавершённый Python-код; не запрашивать новый токен в чат. Включить шаблон
через интерфейс GitHub учётной записью владельца. Реальное железо, отключение
питания, Windows и производственная нагрузка требуют отдельной приёмки. 9A/9B
не реализовывались и не объявляются готовыми. Старые решения ADR-18 о flow/weather
заглушках и общих соединениях заменены этим дополнением.


### Уровни проверки завершения

- SQLite: отдельные request/task соединения, конкурентный rollback/commit, закрытие
  соединений после запроса, nested rollback даже если первая запись во вложенном
  контексте; upgrade исторической БД и идемпотентный backfill ledger.
- MQTT: fake broker, UID replay после архива и после прерванного flow; stop priority,
  worker capacity и cleanup. Доставка настоящим брокером не утверждается.
- HTTP: отсутствие блокировки независимого запроса медленным report, ACL JSON/CSV,
  собственная смена пароля и отзыв других сессий; cookie обновляется на том же host.
- UI: Chromium headless, mock responses, 7 дневных таблиц и missed reason без
  JavaScript ошибок. Это проверка рендера/обработчиков, а не live E2E с ESP32.
- Нагрузка: существующий regression 50×16×96 с порогом 500 мс проходит в полном
  наборе. Это не заменяет длительный production тест с реальной телеметрией.

Дополнительные ограничения данных: старые повреждённые JSON и утраченные дочерние
строки не восстанавливаются из ничего; version=1 явно отмечается legacy_incomplete.
Исторический ledger до ранее удалённых архивом UID не backfill-ится предположениями.
Оценка пропорционального объёма зон не является измерением отдельных расходомеров.
