# ИНСТРУКЦИЯ — ЭТАП 7: погодные корректировки и сезонность

Версия приложения: **0.7.0**. Цель этапа: получать погоду (факт и прогноз) от
Open-Meteo, хранить её в БД, позволить пользователю задавать правила
(`skip` / `reduce_percent` / `increase_percent`) и применять эти правила
**до генерации машинограммы** при компиляции расписания. Уже запущенный полив
правила не прерывают — поправки влияют только на новую машинограмму. При
отсутствии интернета работает offline-политика (`use_last` / `disable_corrections`).

---

## 1. Подготовка окружения

1. Примените миграцию 0009 (таблицы `weather_observations`, `weather_forecasts`,
   `weather_rules`, `weather_rule_applications` + индексы; настройки
   `weather.*`; миграция идемпотентна и обратима):

   ```bat
   python -m server.migrations.0009_weather
   ```

   (либо она применится автоматически при старте сервера — загрузчик миграций
   из `server/app/infra/db.py` подхватит файл по имени).

2. Запустите MQTT-брокер и сервер (как на Этапах 3–6):

   ```bat
   mosquitto -c mosquitto.conf
   python -m uvicorn server.main:app --host 0.0.0.0 --port 8000
   ```

3. Настройки погоды (ключи Артефакта 0.7 §17.7, хранятся в таблице `settings`,
   редактируются со страницы `/weather` или через SQLite):

   | Ключ | Значение по умолчанию | Смысл |
   |---|---|---|
   | `weather.enabled` | `false` | общий выключатель погодных поправок |
   | `weather.latitude` / `weather.longitude` | — | координаты точки для Open-Meteo |
   | `weather.update_interval_min` | `60` | период фонового обновления факт/прогноз |
   | `weather.offline_policy` | `use_last` | `use_last` — брать последние сохранённые данные; `disable_corrections` — пропустить поправки |
   | `weather.rules_enabled` | `true` | точечный выключатель правил (при `false` компилятор игнорирует поправки) |

   Примечание: секция `[weather]` в `config/config.default.toml` не требуется —
   значения читаются из БД-настроек (конфигурация пользователя меняется без
   рестарта). Фоновое обновление реализовано daemon-потоком (apscheduler в
   зависимостях отсутствует — добавлен лёгкий собственный планировщик, см.
   `weather_service.start_weather_updater`).

4. Интернет для Open-Meteo (`https://api.open-meteo.com`) желателен, но не
   обязателен: при недоступности сети клиент возвращает `None`, логирует ошибку,
   а система продолжает работать согласно `weather.offline_policy`.

## 3. Ручная проверка (сценарии из ТЗ)

Чек-лист:

1. Откройте `http://localhost:8000/weather` (логин operator/admin). В меню
   слева ссылка «Погода» — сразу после «События».
2. При пустой БД страница корректно показывает «нет данных» (карточка
   «сейчас» пуста, таблица прогноза пуста) — ошибок нет.
3. Задайте координаты (`weather.latitude`/`weather.longitude`), включите
   `weather.enabled=true` и нажмите «Обновить сейчас» (`POST /api/v1/weather/refresh`) —
   карточка «сейчас» заполнится реальными данными Open-Meteo, в
   `weather_observations` появится запись `source=open_meteo`.
4. **Правило «не поливать при дожде»**: создайте правило
   `rain gt 5 → skip` (scope global). Подготовьте наблюдение с `precip_mm=6`
   (можно вручную INSERT в `weather_observations` или мокрые данные через UI).
   Скомпилируйте расписание («Применить правила вручную» / preview) — шаги
   затронутых зон помечены `skipped` с причиной `weather_skip`, в
   `weather_rule_applications` появилась запись (before_hash/after_hash,
   affected_zones_json). Полив сегодня не полетит на контроллер.
5. **Правило «уменьшить на 30% при жаре»**: создайте `high_temp gt 30 →
   reduce_percent 30`. При температуре 32 °C длительность шагов станет
   `duration * 0.7`, но не меньше `schedule.min_duration_minutes`; аналогично
   `increase_percent` ограничен сверху `schedule.max_duration_minutes`.
6. **Тест правила «в сухую»**: кнопка «Тест» у правила
   (`POST /api/v1/weather/rules/{id}/test`) показывает diff до/после без
   записи в журнал применений.
7. **Offline-политика**: выключите интернет (или поставьте недостижимый DNS) и
   нажмите «Обновить сейчас» — клиент вернёт ошибку, страница покажет баннер
   «Нет связи с погодой — используется последний сохранённый прогноз»
   (`use_last`) либо «Погодные поправки отключены» (`disable_corrections`).
   Компиляция при этом продолжается без сбоев.
8. **Активный полив не прерывается**: запустите полив вручную (zone-open), затем
   создайте `skip`-правило и перекомпилируйте расписание — текущий полив
   доходит до конца, поправка влияет только на следующую машинограмму.
9. ACL: viewer читает `/weather` и GET-эндпоинты, но POST/PUT/DELETE/test
   возвращают 403; operator может создавать правила и тестировать; admin —
   полный CRUD и изменение настроек.
10. Журнал: `GET /api/v1/weather/applications` отдаёт последние применения
    (пагинация, лимит 100).

## 5. Отклонения и решения

- **HTTP-метод изменения правила**: в Артефакте 0.6 указан `PATCH`; реализован
  `PUT /api/v1/weather/rules/{id}` (согласно промпту Этапа 7) — семантика та же
  (частичное обновление тела).
- **Фоновое обновление**: apscheduler отсутствует в зависимостях —
  реализован собственный daemon-поток `WeatherUpdater` с интервалом
  `weather.update_interval_min` (старт/стоп в lifespan `main.py`).
- **Колонки наблюдений**: в `weather_observations` одновременно `precip_mm`
  (спецификация промпта) и `precipitation_mm`/`ts` (совместимость с уже
  работающим rain-delay хуком `core/weather_rules.latest_rain_ts` из Этапа 4) —
  сервис пишет оба поля.
- Нормализация (ADR-13) на этом этапе в погоду не вмешивается — как и
  предписано ТЗ.
