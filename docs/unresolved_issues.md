# Нерешённые проблемы (для аудита)

## 1. Дедупликация событий по event_uid отсутствует (ТЗ §9.2)
**Где:** `server/app/services/schedule_service.py`, `ScheduleService.on_event`.
**Суть:** ТЗ требует игнорировать дубликаты событий по уникальному `event_uid`
(контроллер буферизует события при офлайне и может переотправить их). В коде
дедупликация не реализована: повторное событие с тем же `event_uid` пройдёт
сквозь обработку. Фактически защита есть только на уровне `watering_runs`:
UPDATE по статусу идемпотентен, поэтому наблюдаемых искажений журнала нет —
но явного требования ТЗ это не закрывает.
**Предлагаемое решение:** таблица/множество обработанных `event_uid`
(например `processed_events(uid TEXT PRIMARY KEY, ts)` или LRU-множество в
памяти сервиса + проверка до обработки).

## 2. Обработка ack status="rejected" не отличается от прочего "failed"
**Где:** `schedule_service.py`, `on_schedule_ack`.
**Суть:** при `status="rejected"` версия помечается `failed`, но причина
(`reason` из payload) не сохраняется и не отображается; повторная отправка
этой же версии при следующем hello не блокируется (хеш совпадёт → будет
переотправлена та же отвергнутая машинограмма). Мелкий UX/протокольный долг;
в ТЗ поведение rejected детализировано слабо.

## 3. Зависание тестов Этапа 4 — ИСПРАВЛЕНО (записано для истории)
**Где было:** `_record_planned_runs` вызывалась из-под `self._lock` и сама
захватывала тот же `threading.Lock` (не reentrant) → взаимоблокировка всех
сервисных тестов. Исправлено в этом этапе (снятие вторичного захвата).

## 4. Эмулятор: publish started-события ручного прогона (покрытие тестом)
**Где:** `emulator/controller_sim.py`, `_start_manual_water`.
**Суть:** ручной полив публикует пару событий started/completed (Этап 4,
план→факт). Старый тест Этапа 3 (`test_emulator_fixes.py`) ожидал ровно 1
событие — обновлён под пару (проверка идёт по finished-событию). Если аудит
решит, что manual-прогон обязан публиковать только finished, — надо убрать
emit started в `_start_manual_water`; сейчас оставлен вариант «пара событий»
как более полный контракт.

## 5. Двойное представление программ (watering_programs vs programs) — ИСПРАВЛЕНО
**Где было:** `schedule_service.all_active_controller_ids()` (P1-3, хук
глобальных настроек) выполнял `JOIN watering_programs` — таблицу, которой нет
ни в одной миграции (схемы Этапов 2–4 используют `programs`; компилятор
читает `programs`). На боевой базе запрос падал с `no such table:
watering_programs`, и автоперекомпиляция при изменении settings (`adjustment.*`,
`schedule.apply_policy`) не работала вовсе (ошибка глушилась try/except в
`recompile_all`), т.е. P1-3 для настроек был декоративным.
**Исправление:** приведено к единому источнику истины — таблице `programs`
(миграция 0002). Миграция-синхронизатор не потребовалась: таблица
`watering_programs` в коде/миграциях больше нигде не встречается
(`grep -rn watering_programs server/ emulator/` пуст), сидов в неё тоже нет —
расхождение было только в этом SQL-запросе. Дополнительно: первая правка (JOIN programs ON p.controller_id) вскрывала вторую ошибку того же запроса — колонки controller_id в таблице programs нет (миграция 0002); корректная привязка программы к контроллеру — через program_zones → zones.controller_id, как это делает компилятор (_load_programs). Итоговый запрос использует именно этот путь.
**Тест:** `test_settings_hook_recompiles_all` — изменение глобальной настройки
вызывает перекомпиляцию контроллеров с включёнными программами через `programs`.
